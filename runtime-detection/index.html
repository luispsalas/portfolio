Governed Runtime Detection

A security tool can watch everything a container does. The hard part is deciding what it should alert on, and proving that it does. This is a hands-on lab with Falco on Kubernetes, written up from the business side: the questions to ask, how an answer becomes a rule, and how to show the rule is real.

  • Kubernetes (kind)
  • Falco · eBPF
  • Detection design
  • Oct 2026

Why it matters

Prevention eventually fails: a credential leaks, a dependency is compromised, someone opens a shell where they shouldn't. Runtime detection watches what running workloads actually do and raises an alert when behavior crosses a line. Falco, an open-source CNCF project, does this by reading system calls straight from the Linux kernel, so the workloads it watches need no agent inside them.

The engine is the easy part. Every alert rests on a decision about what counts as abnormal here, and that is a business question before it is a technical one. A rule nobody can trace back to a reason can't be prioritized, tuned or retired, because nobody knows what turning it off would cost.

The system in one picture

The workflow: from a business sentence to a rule

Every rule should trace back to a reason. Here is the chain, followed through one example: protecting a public website from defacement.

  1. Business risk · what could hurt us“Customers must never see unauthorized content on our website.”
  2. Policy · what we commit toProduction web content changes only through the release pipeline.
  3. Control · how we'll knowDetect any write to web content inside a running production container.
  4. Detection spec · precise, owned, testableScope, condition in plain words, known legitimate activity, severity, owner, tests, review date.
  5. Rule · YAML the engine runsA Falco rule built from the spec, field by field (excerpt below).
  6. Test · prove it works, and that it's the rule doing the workSeed the event, check what must stay silent, check that the tool was watching.
  7. Operate · route, triage, tuneAlerts reach someone who can act; false alarms become named, owned exceptions.

↺ And back to the spec: false positives, misses and changes in the business all reopen it. Detections decay quietly as the business changes.

Questions to ask the business

Asked roughly in this order, because each answer narrows the next. The right-hand column is where the answer ends up, so no question is asked for its own sake.

Theme Ask Lands in the rule as
What are we protecting? Which applications would hurt most if tampered with, stopped or leaked? Scope: which namespaces and images are watched
What are we afraid of, or obliged to do? Which scenarios worry you, and which regulations, contracts or audit findings require monitoring? Which rules exist at all; threat-framework tags
What does normal look like? How do software and content reach production? Who may open a shell there, and how? Which agents and vendors run inside? Exceptions, the biggest source of false alarms when left unasked
When it fires, then what? Who is alerted, how fast must they act, and what do they need in the alert to act without digging? Priority, routing and the alert's output fields
How wrong can we afford to be? Which is worse here: a missed attack, or a channel so noisy that people stop reading it? How broad the condition is; staged rollout
Who owns what? Who owns each rule, who may grant an exception and for how long, and who may switch a rule off? Owner, exception register with expiry dates, separation of duties
What must be kept? How long must alerts be retained, who may read them, and must they stand as audit evidence? Forwarding destination and retention
Is this the right tool? Should this be prevented rather than detected? Do we need to know which person did it? Possibly no rule at all; identity comes from the platform's audit log, not from system calls

How the answers become a rule

The defacement example, written as a production-ready Falco rule. Each part maps to an answer above: the namespace list is the scope, the exception is what normal looks like (the release pipeline may write content), the priority is how fast someone must act, and the tags tie it to the policy and the threat (MITRE ATT&CK T1491, Defacement).

- rule: Web content modified at runtime in production
  condition: >
    open_write and container
    and k8s.ns.name in (prod_web_namespaces)
    and fd.name startswith /usr/share/nginx/html/
  exceptions:
    - name: release_pipeline     # named, owned, with a review date
      fields: [container.image.repository, proc.name]
      comps: [=, =]
      values:
        - [registry.example.com/web/content-sync, rsync]
  priority: ERROR
  tags: [web, filesystem, mitre_impact, T1491, policy_WEB-01]

Excerpt; names are placeholders. The full rule loads cleanly in Falco 0.45, and a deliberately broken copy is rejected, which shows the validation check itself works. Owner, response, routing and retention don't live in the rule: they live in the spec beside it, and in the platform that receives the alerts.

Severity is a business decision

Falco's own guideline grades the behavior: writing state is ERROR, an unauthorized read is WARNING, unexpected behavior is NOTICE. A business needs to grade impact and confidence, then map that to a response. Writing the grid down once stops priority from becoming each author's mood.

Clearly malicious Needs investigation
Crown-jewel system CRITICAL · page someone now ERROR · triage the same day
Ordinary system ERROR · triage the same day WARNING / NOTICE · review queue

Proving the rule is real

A rule that fires once has only been shown to fire. The test ran the same three actions twice, once with the rule enabled and once with it switched off, changing nothing else.

Action Why Rule on Rule off
Write a page into the web folder The event the rule targets fires ✓silent ✓
Write a file somewhere else The rule must not fire on just any write silent ✓silent ✓
Read the password-hash file A built-in rule must fire, proving Falco was watching fires ✓fires ✓

The third row is the one that matters. Without it, the silence in the second run would look exactly like a security tool that had stopped watching.

What the lab surfaced

  • The loudest alerts came from the platform itself. Routine pod creation produced 15 Critical alerts. The cause, confirmed in the alert data: Kubernetes' node agent mounting storage for new pods. “Normal” has to include the platform, not just the application, and a Critical label is the rule's opinion of the behavior, not a measure of real danger.
  • Detecting is not the same as attributing. Falco caught activity in a container outside the cluster but couldn't name it, and every alert reports the container's own user rather than the person who ran the command. Who did it comes from Kubernetes' audit log. If the business needs accountability, the design has to include both.
  • Whoever can edit the rules can switch off the alarm. One changed line silenced the custom rule in the test. Who may change or disable a rule is a control in its own right.
  • Testing didn't catch the design mistakes; a review did. The first version of the custom rule passed every test, yet used the wrong priority for its kind of event and fired in every environment. Only comparing it against a written standard showed that.

How it was built

A single-node Kubernetes cluster (kind) and Falco 0.45, installed with Helm and using its built-in eBPF probe, on a Linux machine that also runs other services. It needed no administrator rights and left those services untouched. Every step is a script, every tool download was checksum-verified, and the whole lab tears down and rebuilds in under five minutes.

It was built with an AI coding agent. Every install command came from documentation fetched during the run, never from the model's memory. The record lists seven places where the agent's output needed correcting. Three of its failures were silent, with no error, just missing output, and each was caught the same way: by checking for output that should have been there.
